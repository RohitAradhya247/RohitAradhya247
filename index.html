      OpsPilot

      An LLM agent diagnoses the root cause of failures in microservice systems. I own the layer that decides whether to trust that diagnosis.

      Every diagnosis must cite evidence. My verifier looks each citation up in a DuckDB and Parquet store of metrics, logs, traces and call graphs, then runs six checks against it.

      • Cited evidence is real and matches
      • The root cause shows an anomaly
      • Its onset comes before the symptoms
      • The failure path follows real calls
      • The fault’s signature moves the right way
      • At least two signal types agree

      What the router decides

      ✓AcceptEvery check that applies passes, and at least one applies.
      ↺Reject and retryAny check fails. The agent gets feedback on what failed and up to two more tries.
      ?UnsureEvidence is missing. Final, because retrying can’t create missing data.

      Every verdict goes into an audit log that replays exactly, and raw log text can never be the only proof.

      Phases 0 to 2 done

      CoreOps

      An end-to-end AI operations platform for an e-commerce company: a tested data warehouse, a secure role-based API, dashboards, a chatbot and AI agents with a verifier that checks every answer against the data.

      It models one mid-size e-commerce company using the real Olist dataset, about 100,000 orders from 2016 to 2018, and covers the work a company actually runs on: sales reporting, delivery performance, customer satisfaction, support triage, forecasting and management reporting.

      The most interesting problem so far

      The end of the dataset looks like a sales collapse: 6,512 orders in August 2018, then 16 in September. It isn’t falling demand. Reviews stop on 31 August and the slowest deliveries vanish in the final weeks, so orders that hadn’t finished yet simply weren’t exported.

      I flag those rows instead of deleting them, and only count delivery and review outcomes for orders at least 49 days old, the point by which 99% would have arrived. Without that cut-off the late-delivery rate reads 6.85% instead of 7.07%, so the business would look better than it is.

      An API that can’t leak or lie

      Phase 2 added a secure API with four least-privilege roles, from execs who see only aggregates to support staff who see orders but not revenue. It runs as a restricted database role, and every request goes into an append-only audit log the app itself can’t tamper with. The log fails closed: if it can’t be written, no data leaves the API.

      Its 313 automated tests include one built from the app’s own route table, so any new endpoint without a permission check fails CI. Through the API, the Phase 1 figures reproduce exactly: core GMV of BRL 13,312,577.43 and a 7.07% late rate.

      How it’s built
